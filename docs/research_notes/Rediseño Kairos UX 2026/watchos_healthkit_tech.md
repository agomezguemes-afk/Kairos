# iPhone + Apple Watch training app on Expo/RN in late 2026: technical feasibility map

Research date: 2026-11-08. Baseline codebase: RN 0.81 / Expo SDK 54, dev client, EAS Build from Windows, occasional Mac.
Research budget: about 15 tool calls. Some Apple reference pages and GitHub READMEs could not be fetched (403s or empty results). Those items are listed under Gaps. Claims based only on model background knowledge are labelled "unverified".

## 1. watchOS: React Native on the watch, native SwiftUI targets in Expo, EAS from Windows, WatchConnectivity and App Groups

### Takeaway
Expo and Meta still offer no official React Native support for watchOS. A community project, `@appsent-co/react-native-watchos`, now runs a Hermes JS bundle on the watch through a SwiftUI renderer, but it is unproven and needs a Mac with Xcode. The production-grade route is a native SwiftUI watch target generated by `@bacons/apple-targets` (expo-apple-targets) at prebuild. EAS can build and sign it, though signing multiple targets is only "theoretically" automatic and lightly tested by the author.

### Cited Findings
- `@bacons/apple-targets` supports about 50 Apple target types, including `watch`, `watch-widget`, `widget` (which also covers Live Activities), `app-intent`, `clip`, `share`, `notification-content`, `wallet` and `matter`. TV Top Shelf, Finder Sync and Mail extensions are not supported. — [EvanBacon/expo-apple-targets (GitHub)](https://github.com/EvanBacon/expo-apple-targets)
- Each subfolder of `/targets` holds an `expo-target.config.js`. Prebuild links these folders into Xcode as a virtual `expo:targets` folder, and `_shared` folders link files into several targets. — [expo-apple-targets](https://github.com/EvanBacon/expo-apple-targets)
- On EAS signing, the README says code signing is "theoretically handled entirely by EAS Build", and the author has tested it end-to-end with only one widget project. App Clip signing is not automated: it needs Xcode's Signing tab after prebuild. The npm README also says target entitlements are "not currently used in EAS Capability signing". — [expo-apple-targets GitHub](https://github.com/EvanBacon/expo-apple-targets); [npm summary via search](https://www.npmjs.com/package/%40bacons%2Fapple-targets)
- Stated requirements: CocoaPods 1.16.2, Xcode 16 on macOS 15, Expo SDK 53 or later. The `@bacons/xcode` parser it depends on is described as "very untested". — [expo-apple-targets](https://github.com/EvanBacon/expo-apple-targets)
- The upstream project has been described as "highly experimental and not part of any official Expo workflow". Forks such as Maroon-Rides/expo-apple-targets advertise added watchOS support, which suggests watch support in upstream has historically lagged. — [Maroon-Rides fork](https://gh.hhj520.top/Maroon-Rides/expo-apple-targets); [npm @bacons/apple-targets](https://npmjs.com/package/@bacons/apple-targets)
- App Groups: declare the group in `app.json` under `ios.entitlements` and repeat it in the target's `expo-target.config.js`. Shared data goes through `ExtensionStorage`, a wrapper around `NSUserDefaults(suiteName:)`. — [expo-apple-targets](https://github.com/EvanBacon/expo-apple-targets)
- `@appsent-co/react-native-watchos` runs React JS UI on the watch. The watch loads its own Hermes bundle and renders through SwiftUI with package-specific components such as `VStack` and `Text`, behind a watchOS-safe shim for `react-native`, so it is not full RN. It also has its own WatchConnectivity feature. It requires macOS with Xcode 16 or later and the watchOS SDK, Expo SDK 54 or later, Hermes, and `@bacons/apple-targets`. — [react-native-watchos install docs](https://appsent-co.github.io/react-native-watchos/getting-started/installation); [expo plugin page](https://appsent-co.github.io/react-native-watchos/expo-plugin)
- `react-native-watchos` limitations: first launch takes about 10 s for Hermes to start on the watch; Fast Refresh drops when the watch suspends; physical watches need `RNW_DEV_SERVER_HOST`/`PORT`; Metro must be wrapped with `withWatchosMetro`. The docs do not mention EAS and give no maturity or version statement. — [react-native-watchos docs](https://appsent-co.github.io/react-native-watchos/getting-started/installation)
- An older community example adds a Watch App and complication to an Expo managed project built on EAS, using the experimental `extra.eas.build.appExtensions` setting. — [mpiannucci/eas-widget-watchos-example](https://gh.r-mj.com/mpiannucci/eas-widget-watchos-example)
- `@kingstinct/expo-apple-targets` and `@duell10111/apple-targets` are other published forks of the same plugin. — [npm @kingstinct/expo-apple-targets](https://www.npmjs.com/package/%40kingstinct%2Fexpo-apple-targets); [unpkg @duell10111/apple-targets README](https://unpkg.com/@duell10111/apple-targets@0.1.14/README.md)

### Inferences
- Recommended: keep the iPhone app in RN/Expo and write the watch app in native SwiftUI under `/targets/watch`, generated by `@bacons/apple-targets`. The watch app owns `HKWorkoutSession`, live metrics and set logging, and syncs with the phone over WatchConnectivity, with HealthKit as the source of truth for workouts. JS on the watch (`react-native-watchos`) is a research spike only: a 10 s cold start is unacceptable for a "start workout" interaction, and the project has no stated maturity.
- From Windows you can write the Swift files and build and sign with EAS, but you cannot compile, preview or debug SwiftUI locally. A Mac with Xcode is needed for SwiftUI previews, the watch simulator, the debugger, Instruments, the first-time setup of signing and capabilities for a new target, and diagnosing EAS build failures. Plan Mac sessions for the watch target.
- Treat EAS multi-target signing (main app plus watch app plus widget extension, each with its own provisioning profile and the HealthKit and App Groups capabilities) as a risk to de-risk in week one with a hello-world watch target.
- Use WatchConnectivity (`WCSession`) on both sides: messages for live events while both apps are reachable, `transferUserInfo` for guaranteed delivery of logged sets, and application context for the current plan. Exposing this to JS on the phone needs a small Expo Module in Swift, which can live in `modules/`. App Groups are for sharing between the app and its extensions on the same device, not between phone and watch. (Unverified framework knowledge: App Group containers do not sync across devices.)

### Gaps
- I found no first-hand 2026 report of a shipped Expo + SwiftUI watch app built only on EAS from Windows. Validate this with a spike.
- I could not get the current `@bacons/apple-targets` version or its compatibility with Expo SDK 56–58. The GitHub releases section was empty in the capture, and npm returned 403.
- I did not verify whether `react-native-watchos` supports EAS or has production apps.
- I found no source for a maintained WatchConnectivity Expo module. Searches turned up none beyond the one built into `react-native-watchos`. `react-native-watch-connectivity` exists but its 2026 status was not checked.

## 2. HealthKit and WorkoutKit in 2026: workout sessions, mirroring, iPhone-only sessions, zones, effort, Workout Buddy, metrics, permissions

### Takeaway
iOS 26 brought `HKWorkoutSession` and `HKLiveWorkoutBuilder` to iPhone and iPad (WWDC25 session 322), so phone-only workouts no longer need a watch. Watch-to-phone mirroring (watchOS 10 / iOS 17+) works but has reported reliability bugs in 26.x. iOS 27 and watchOS 27 add native heart-rate and cycling-power zones (WWDC26 session 207). Effort scores exist, but writing a third-party effort score is reported as flaky. Workout Buddy remains a first-party feature, and I found no third-party API for it.

### Cited Findings
- WWDC25 session 322, "Track workouts with HealthKit on iOS and iPadOS", covers running a workout session on iPhone and iPad, how it differs from Apple Watch, and crash recovery. All workout activity types are available on iPhone and iPad, but those devices have no heart-rate sensor. — [WWDC25 322](https://developer.apple.com/videos/play/wwdc2025/322)
- Watch workout code can be reused on iPhone and iPad with few changes. — [WWDC25 322 (pt-BR transcript)](https://developer.apple.com/br/videos/play/wwdc2025/322/?time=7)
- Before iOS 26, HealthKit workout tracking was possible only on Apple Watch. From iOS 26 the same APIs are available on iPhone and iPad. — [Create with Swift](https://www.createwithswift.com/tracking-workouts-with-healthkit-in-ios-apps/)
- The phone is far more likely to be locked during a workout, and health data is unavailable while it is locked. The session pairs workouts with Live Activities and Siri for the lock-screen experience. — [WWDC25 322 (ko)](https://developer.apple.com/kr/videos/play/wwdc2025/322/?time=444); [WWDC25 322 (jp)](https://developer.apple.com/jp/videos/play/wwdc2025/322/?time=218)
- iPhone workouts use the same `HKLiveWorkoutBuilder` as the watch. The session has six states. (Secondary source.) — [Blake Crosley, HKWorkoutSession lifecycle](https://blakecrosley.com/blog/watchos-workout-lifecycle)
- Mirroring: `startMirroringToCompanionDevice()` makes a watch session available on the iPhone. A working pattern calls `prepare()` first, and a separate post covers sending the initial configuration ("remote delegate not set up" error). Apple's `stopMirroringToCompanionDevice` is available on watchOS 10.0+. — [nonstrict.eu blog](https://nonstrict.eu/blog/2024/hkworkoutsession-remote-delegate-not-setup-error); [Apple docs](https://developer.apple.com/documentation/healthkit/hkworkoutsession/stopmirroringtocompaniondevice(completion:).md); [Apple sample "Building a multidevice workout app"](https://developer.apple.com/tutorials/data/documentation/healthkit/building-a-multidevice-workout-app.md)
- Mirroring reliability: one developer forum thread reports mirroring failures on watchOS 26.0.2 / iOS 26.0.1, with a workaround of calling `startMirroringToCompanionDevice` after the session is prepared or running. Reconnecting can hang without throwing. — [Apple Dev Forums 804276](https://developer.apple.com/forums/thread/804276)
- Starting the watch app from the phone: `HKHealthStore.startWatchApp(with:completion:)`. — [Apple docs](https://developer.apple.com/tutorials/data/documentation/healthkit/hkhealthstore/startwatchapp(with:completion:).md)
- Effort score: developers report that `relateWorkoutEffortSample` completes without error but no effort shows in Fitness. One developer heard it can take weeks or months before watchOS computes effort for third-party apps. — [Apple Dev Forums "Workout Effort Scores"](https://developer.apple.com/forums/thread/764884)
- New in iOS 27 / watchOS 27 (WWDC26 session 207): native heart-rate and cycling-power zones. — [WWDC26 207](https://developer.apple.com/videos/play/wwdc2026/207)
  - `HKWorkout.zoneGroupsByType` and `HKWorkoutActivity.zoneGroupsByType` are keyed by `HKQuantityType`; each `HKWorkoutZoneGroup` holds a `configuration` and `zoneDurations`.
  - The live delegate method `workoutBuilder(_:didUpdateWorkoutZone:)` delivers an `HKLiveWorkoutZoneUpdate` and fires only when the zone changes.
  - `builder.zoneConfiguration(for:)` returns the preferred configuration. `setCustomZoneConfiguration(_:for:)` must be called before `beginCollection`.
  - Custom configurations need 3–9 zones, apply to one workout only and are not persisted by HealthKit, so the app must store them.
  - Preferred heart-rate zones are calculated from age and resting heart rate, or set by the user in Health Settings, and sync across devices.
  - To compare workouts, re-bucket raw samples into a consistent number of zones.
- watchOS 27 product changes: Workout Buddy no longer needs the iPhone nearby, outdoor route maps are cleaner, and treadmill distance is more accurate. Exact method-level API details were described as "still emerging". — [AppleInsider](https://appleinsider.com/articles/26/06/08/coaching-wellness-features-ai-make-the-biggest-impact-in-watchos-27); [Digit](https://www.digit.in/features/wearable-devices/how-to-exercise-better-with-watchos-27-using-siri-ai-and-workout-buddy.html); [definesolutions](https://definesolutions.pages.dev/journal/watchos-27-whats-new)
- Coverage noted that Apple did not ship a full "Siri AI health coach" in watchOS 27. — [TechRadar](https://techradar.com/health-fitness/watchos-27-may-have-improved-the-apple-watchs-ai-features-but-a-siri-ai-health-coach-was-needed-to-rival-the-google-fitbit-air)

### Inferences
- Architecture for a sport-agnostic app:
  - With a watch: the watch runs `HKWorkoutSession` and `HKLiveWorkoutBuilder` (heart rate, energy, distance, zones) and mirrors to the phone; the phone shows the rich UI.
  - Without a watch (iOS 26+): the phone runs the session itself, using Bluetooth heart-rate straps or AirPods heart rate where available (unverified), and shows a Live Activity because the phone is usually locked.
  - Strength and set-based training: HealthKit has no "sets/reps" model, so Kairos's own store holds sets, reps and load, linked to the `HKWorkout` by UUID or metadata.
- Zones in iOS 27 give the adaptive engine a free, standardized intensity signal. Store custom zone configurations in Kairos's data model, because HealthKit does not persist them.
- Do not make the adaptation logic depend on Apple's effort score being written or read back reliably for third-party workouts. Compute Kairos's own load (for example sRPE × duration, or time in zones) and treat Apple's effort score as optional input.

### Gaps (unverified background knowledge, not sourced this session)
- **WorkoutKit:** `CustomWorkout`, `WorkoutPlan`, `WorkoutScheduler` (watchOS 10 / iOS 17+) let an app schedule structured workouts (warm-up, interval blocks, cooldown, goals and alerts) that appear in Apple's Workout app on the watch. They mainly cover cardio-style activities and are not designed for strength set prescription. I did not fetch Apple docs to confirm 2026 status or iOS 26/27 additions.
- **Training load (watchOS 11):** I could not fetch the `HKWorkoutEffortScore` and `estimatedWorkoutEffortScore` quantity types or `relateWorkoutEffortSample(_:with:activity:)` docs, so exact availability is unconfirmed.
- **Metrics and permissions:** HR, HRV (SDNN), resting HR, VO2max, sleep stages (`HKCategoryValueSleepAnalysis` with REM, core and deep since iOS 16), respiratory rate, wrist temperature and similar types are expected to be readable with per-type read and write authorization. Apps cannot tell whether read access was denied. Background delivery uses `enableBackgroundDelivery` plus the `com.apple.developer.healthkit.background-delivery` entitlement. None of this was re-verified this session.
- **Workout Buddy / Apple Intelligence hooks:** I found no source showing a public API for third-party apps to plug into Workout Buddy. App Intents and Siri integration for workouts are mentioned in WWDC25 322, but I did not get the details.

## 3. RN HealthKit libraries in 2026

### Takeaway
`@kingstinct/react-native-healthkit` is the leading choice. It is at v14.x, built on Nitro Modules, ships an Expo config plugin with a background option, and supports queries, saves, subscriptions and anchored queries. Its README does not document live workout sessions, mirroring or WorkoutKit, so those must be written in native Swift (an Expo Module) or on the watch.

### Cited Findings
- Current version is 14.0.1, and it requires `react-native-nitro-modules`. — [jsDelivr package.json](https://cdn.jsdelivr.net/npm/@kingstinct/react-native-healthkit@14.0.1/package.json)
- Features: 75+ workout activity types for query, save and subscribe; workouts returned as proxies with methods such as `getWorkoutRoutes`; a `useMostRecentWorkout` hook; `subscribeToChanges(type, cb)`; anchored queries that return new and deleted samples, useful for sync. — [README 14.0.1](https://cdn.jsdelivr.net/npm/@kingstinct/react-native-healthkit@14.0.1/README.md)
- Expo plugin options are `NSHealthShareUsageDescription`, `NSHealthUpdateUsageDescription` and `background` (boolean). It needs a dev client and does not run in Expo Go. — [README](https://cdn.jsdelivr.net/npm/@kingstinct/react-native-healthkit@14.0.1/README.md)
- Limitations: — [README](https://cdn.jsdelivr.net/npm/@kingstinct/react-native-healthkit@14.0.1/README.md)
  - Querying or subscribing to a type without having requested permission crashes the app.
  - Document types are read-only.
  - Clinical records are partial and need v3.x or a specific branch.
  - Metadata keys are serialized differently (`HKExternalUUID`).
  - Units are strings.
  - The README does not mention workout sessions, mirroring or WorkoutKit.
- Older snapshots on index sites show v8.x in January 2025, so the library has had about 6 major versions since. — [repositorystats](https://repositorystats.com/kingstinct/react-native-healthkit)
- Forks exist, for example `runna-app/react-native-healthkit-2` (Runna is a running-plan app), which suggests production use in the training-app category. — [runna-app fork](https://gh.hhj520.top/runna-app/react-native-healthkit-2)
- `react-native-health` remains on npm. — [jsDelivr](https://www.jsdelivr.com/package/npm/react-native-health)

### Inferences
- Use `@kingstinct/react-native-healthkit` on the phone for reads (history, HRV, sleep, VO2max, zones once the library exposes them), workout saves and subscriptions. Write a thin custom Expo Module in Swift for anything the library lacks: iPhone `HKWorkoutSession` (iOS 26), mirrored-session delegate, WorkoutKit scheduling, iOS 27 zones.
- Guard every query behind its authorization request, given the documented crash.
- `react-native-health` looks like the legacy option. I did not verify its maintenance status, so I would not choose it for a 2026 build.

### Gaps
- I did not verify whether kingstinct v14 exposes `HKWorkoutSession`, `startWatchApp`, effort score or iOS 27 zones. Check the repo source and CHANGELOG.
- `react-native-health` release cadence in 2026 is unknown.

## 4. Live Activities, Dynamic Island, widgets, App Intents from Expo

### Takeaway
`expo-widgets` was promoted to stable in SDK 56. It authors home-screen widgets, Lock Screen widgets and Live Activities, including Dynamic Island, in JSX using `@expo/ui/swift-ui` components, with APNs push updates. `@expo/ui` SwiftUI was also declared stable in SDK 56. Interactive buttons work on iOS 17+. App Intents and watch complications are not covered by `expo-widgets`; for those, use `@bacons/apple-targets` (`app-intent`, `watch-widget`) with native Swift.

### Cited Findings
- SDK 56 changes: — [Expo SDK 56 changelog](https://expo.dev/changelog/sdk-56.md)
  - Expo Widgets for iOS are promoted to stable.
  - Widgets and Live Activities have full access to the environment and no longer need pre-rendering.
  - Expo UI's SwiftUI and Jetpack Compose APIs are stable and included in the default template and in Expo Go.
- `expo-widgets` (docs versioned with SDK 58) surfaces: — [expo-widgets docs](https://docs.expo.dev/versions/latest/sdk/widgets/)
  - iOS home and Lock Screen widgets.
  - Live Activities, covering the Lock Screen banner and Dynamic Island compact, minimal and expanded views.
  - A small Live Activity banner on CarPlay and watchOS. Watch complications are not mentioned.
  - Android widgets, opt-in.
- `expo-widgets` authoring and runtime: — [expo-widgets docs](https://docs.expo.dev/versions/latest/sdk/widgets/)
  - Write JSX with `@expo/ui/swift-ui` and mark components with a `'widget'` directive. They compile to a separate bundle, and prebuild generates the extension.
  - The widget runtime is isolated: no hooks, state, context, async work or imports.
  - `groupIdentifier` defaults to `group.<bundle id>`.
- `expo-widgets` updates and interactivity: — [expo-widgets docs](https://docs.expo.dev/versions/latest/sdk/widgets/)
  - Push-to-start tokens (iOS 17.2+) and per-activity push tokens, sent over APNs with the `liveactivity` push type.
  - `Button onPress` returns new props that persist without the app running (iOS 17+).
  - App Intents are not mentioned.
- `@bacons/apple-targets` supports `app-intent`, `widget`/Live Activities and `watch-widget` targets for anything `expo-widgets` does not cover. — [expo-apple-targets](https://github.com/EvanBacon/expo-apple-targets)

### Inferences
- For a workout Live Activity on the phone, which is essential for iOS 26 phone-only workouts because the phone is locked, `expo-widgets` is production-viable on SDK 56 or later. Kairos's SDK 54 is too old for the stable version, which is another reason to upgrade.
- Watch complications or Smart Stack widgets and App Intents for Siri, Shortcuts and the Action Button ("Start Kairos session") should be native Swift targets through apple-targets. The prebuild model means EAS builds them, but a Mac is useful for previewing the SwiftUI.
- `react-native-live-activities` and similar third-party libraries are now largely superseded by `expo-widgets` for Expo apps. This is inferred from `expo-widgets` reaching stable; I did not check those libraries' status.

### Gaps
- I did not find whether the EAS Build docs explicitly cover `expo-widgets` extension signing. The docs say only to use dev builds and prebuild.
- I have no source on an Expo-first App Intents API.

## 5. Migrate to Expo SDK 55/56/57/58 and Expo Router native tabs / Liquid Glass?

### Takeaway
The latest SDK is 58 (around October 2026): RN 0.88, iOS 27 support, Xcode 27.1 on EAS, native tabs promoted out of `unstable-`, and a Liquid Glass stack header by default on iOS 26+. Kairos on SDK 54 is four SDKs behind. Upgrade directly to SDK 58, staged through 56 and 57 because breaking changes accumulate. Adopt Expo Router with native tabs for system tab bars and Liquid Glass.

### Cited Findings
- SDK 56, released May 21, 2026: RN 0.85, React 19.2, Xcode 26.4 minimum, iOS minimum 16.4, prebuilt XCFrameworks (median clean iOS build about 16% faster, opt out with `EXPO_USE_PRECOMPILED_MODULES=0`), Expo UI stable, Widgets stable. An August 27 note flags a Hermes V1 memory regression with reanimated and worklets and recommends SDK 57. — [SDK 56 changelog](https://expo.dev/changelog/sdk-56.md)
- SDK 57, released June 30, 2026: RN 0.86 with no intended breaking changes from 0.85; reanimated 4.5, worklets 0.10, gesture-handler 2.32; the Hermes V1 memory regression is fixed in a later patch; upgrade with `npx expo install expo@^57.0.0 --fix`. — [SDK 57 changelog](https://expo.dev/changelog/sdk-57); [releases.sh digest](https://releases.sh/collections/frontend-frameworks/digest/2026-06-29)
- SDK 58 (upgrade guide dated October 21, 2026): — [How to upgrade to SDK 58](https://expo.dev/blog/how-to-upgrade-to-sdk-58)
  - RN 0.86 → 0.88, iOS 27 support, EAS `sdk-58`/`latest` images on Xcode 27.1.
  - Native tabs move from `expo-router/unstable-native-tabs` to `expo-router/native-tabs`.
  - The stack header is transparent with Liquid Glass by default on iOS 26+.
  - `@expo/ui` becomes an optional peer dependency, needed for `Stack.Toolbar`.
  - Prebuild generates `SceneDelegate.swift`.
  - Breaking changes: strict TypeScript API by default (no deep `react-native/Libraries/*` imports), `InteractionManager` removed in favour of `requestIdleCallback`, `ImageBackground` deprecated, iOS 27 apps are resizable so `ScreenOrientation.lockAsync` may be ignored, Router navigation core reworked so `expo-router/react-navigation` imports may break.
- `expo-glass-effect` (Liquid Glass view) works only on iOS 26+. — [Expo docs v57 glass-effect](https://docs.expo.dev/versions/v57.0.0/sdk/glass-effect/)
- A secondary source claims apps below SDK 54 can hit silent bugs when built with the iOS 26 SDK, and that SDK 56 adopted the UIKit scene lifecycle. This is unverified against Expo docs. — [Mindbowser](https://www.mindbowser.com/?p=116412)

### Inferences
- A redesign is the right moment to move to Expo Router with native tabs and SDK 58. The current React Navigation tree (Welcome / Setup / Dashboard tabs) maps cleanly to a file-based layout.
- iOS minimum 16.4 is fine, since iPhone-only workouts and Foundation Models need iOS 26 anyway and older versions can feature-gate.
- Upgrade order:
  1. SDK 54 → 56: React 19.2 and RN 0.85 come in, and the reanimated and worklets bumps are the riskiest for Kairos's heavy Reanimated use.
  2. → 57: picks up the Hermes memory fix.
  3. → 58: strict TypeScript, scene delegate, router rework.
- Keep each step as a bisectable commit, per CLAUDE.md.
- `@bacons/apple-targets` must be verified against SDK 58 prebuild, which now regenerates native directories ("prebuild now clears native dirs" per the RN 0.86 release note). — [releases.sh](https://releases.sh/release/rel_aH7NaXbDXMlY2_I-Ak0D0)

### Gaps
- I did not confirm an exact SDK 58 release date (the blog is dated October 21, 2026) or whether SDK 58 has a minimum-iOS change.
- I have no source on whether Expo plans an SDK 59 before year-end.

## 6. On-device AI: Apple Foundation Models from RN; privacy versus cloud

### Takeaway
Apple's Foundation Models framework (iOS 26+, Apple Intelligence devices only) is reachable from RN through several community packages. The most credible is Callstack's `@react-native-ai/apple`, which integrates with the Vercel AI SDK and adds embeddings, transcription and speech. Callstack also has a "Core AI" provider for iOS 27 that runs exported `coreai-models` on device. Expo has a `docs.expo.dev/.../sdk/ai` page, but I could not confirm its contents.

### Cited Findings
- `@react-native-ai/apple`: — [callstackincubator/ai](https://github.com/callstackincubator/ai)
  - Text generation via Apple Foundation Models needs iOS 26+ and an Apple Intelligence device.
  - Embeddings via `NLContextualEmbedding` (512-d) need iOS 17+.
  - Transcription via SpeechAnalyzer needs iOS 26+.
  - TTS via AVSpeechSynthesizer.
  - Plugs into Vercel AI SDK `generateText` and `embed`. Package 0.13+ maps to AI SDK v7.
  - The repo has about 1.4k stars. It also offers a Llama (GGUF via llama.rn) provider, Android Gemini Nano via ML Kit GenAI, and a Core AI provider (iOS 27, Xcode 27, physical device).
- Callstack announced the package as a preview release. — [Callstack blog](https://callstack.com/blog/on-device-apple-llm-support-comes-to-react-native)
- Alternatives: — [search summary](https://www.pkgstats.com/pkg:expo-apple-foundation-models); [expo-ai-kit](https://cdn.jsdelivr.net/npm/expo-ai-kit@0.12.0/README.md); [react-native-apple-intelligence](https://gh.r-mj.com/corasan/react-native-apple-intelligence)
  - `expo-apple-foundation-models`: text, structured output and tool calling.
  - `expo-foundation-models`: iOS 26+.
  - `react-native-apple-intelligence`: a Nitro module with tool calling and streaming.
  - `@drewalth/react-native-foundation-models`: experimental.
  - `expo-ai-kit`.
- Expo has an "ai" SDK reference page under `unversioned`, which suggests an upcoming or new first-party module. Contents were not fetched. — [docs.expo.dev unversioned/sdk/ai](https://docs.expo.dev/versions/unversioned/sdk/ai)

### Inferences
- Use a hybrid AI design:
  - On-device, Foundation Models where available: summaries, natural-language set logging ("3x8 at 80"), structured extraction into Kairos's schema with tool calling, and privacy-sensitive analysis of health data. These features need a fallback for devices without Apple Intelligence.
  - Cloud LLM: plan generation and long-horizon analysis, where the roughly 3B-parameter on-device model is weaker (unverified size).
- Privacy: HealthKit data sent to a cloud LLM triggers App Store guideline and health-data disclosure obligations and needs explicit consent. On-device inference avoids that. (Inference; I did not fetch the App Review Guidelines.)
- The adaptive training core (progression, deload, readiness from HRV and sleep) should stay deterministic and on device, with the LLM explaining rather than deciding. This matches CLAUDE.md's "AI evolves with data" and keeps behaviour testable.

### Gaps
- I did not fetch Foundation Models context-window size, guardrail behaviour, or whether it runs on watchOS (unverified: it does not, as of 26).
- The structured output and tool calling support in `@react-native-ai/apple` was not confirmed on the fetched page. Alternatives claim both.
- The contents of the Expo `sdk/ai` page are unknown.

## 7. Local-first data: SQLite, Supabase sync, conflicts

### Takeaway
`expo-sqlite` keeps maturing: SDK 56 added native ArrayBuffer blobs and session changesets, which are useful for building sync. For sync with Supabase, PowerSync is the established managed option. Its default is last-write-wins through `SupabaseConnector`, and custom conflict resolution lives in the backend `uploadData` path. A hand-rolled outbox queue (SQLite, then sync queue, then Supabase) is the do-it-yourself alternative.

### Cited Findings
- SDK 56 `expo-sqlite` adds native `ArrayBuffer` support for blob columns and bind parameters, plus session changesets. — [SDK 56 changelog](https://expo.dev/changelog/sdk-56.md)
- PowerSync with Supabase uses last-write-wins by default through `SupabaseConnector` and can be customized. PowerSync leaves conflict resolution to the backend. — [PowerSync blog](https://powersync.com/blog/offline-first-apps-made-simple-supabase-powersync); [Supabase partner page](https://supabase.com/partners/integrations/powersync); [PowerSync write patterns](https://telemetry-landing.pages.dev/blog/write-patterns-for-powersync/)
- PowerSync published a TanStack DB integration covering last-write-wins plus domain-specific and manual resolution (February 2026 changelog). — [PowerSync Feb 2026](https://powersync.com/blog/powersync-changelog-february-2026.md); [TanStack DB + PowerSync](https://powersync.com/blog/offline-first-apps-with-tanstack-db-and-powersync)

### Inferences
- Move from Zustand + AsyncStorage to SQLite as the source of truth: `expo-sqlite` with Drizzle, or PowerSync's SQLite. Training logs are append-mostly (sets, sessions), so conflicts are rare.
  - Model sets and sessions as immutable events with UUIDs, which merge as a union.
  - Model plans and templates as LWW-per-field with `updated_at` and a device ID.
- HealthKit stays authoritative for physiological samples. Store HK UUIDs and anchors, not copies of raw heart-rate streams.
- The watch should keep its own small store (SwiftData or SQLite) and push completed sets to the phone through `transferUserInfo`. The phone writes them to SQLite, and SQLite syncs to Supabase.

### Gaps
- I did not verify PowerSync's current RN/Expo SDK version, pricing or self-host option, or alternatives such as ElectricSQL, Triplit, Instant or Legend-State with Supabase in 2026.
- I have no source comparing `expo-sqlite` changesets with PowerSync for this use case.
